# MacroLog

Personal calorie/macro tracking PWA for Colin. Single user, single active device at a time. Hosted on GitHub Pages at `https://colinswhardy.github.io/claudemacro/` (repo `colinswhardy/claudemacro`). Backend is a single production Supabase project (Postgres + PostgREST + GoTrue auth) — there is no staging environment and no test database; every push to `main` deploys straight to the live site and the live DB.

## Files

- `index.html` (~3500 lines) — the entire app: HTML shell + `<style>` + one big inline `<script>`. No build step, no framework, no bundler, no TypeScript, no npm dependencies. A second tiny `<script>` at the bottom just registers the service worker.
- `sw.js` — service worker. Network-first for the app shell (cache name `macrolog-v2`), so a redeploy is picked up on next load instead of being stuck on a stale cache.
- `manifest.json` — PWA manifest.
- `supabase/schema.sql` + `supabase/README.md` — the DB schema and one-time setup walkthrough. Six tables MacroLog owns, all RLS-scoped to `auth.uid() = user_id`: `food_log_entries`, `weight_entries`, `recipes`, `custom_barcodes`, `user_settings`, `user_app_data` (favorites/recentFoods/foodCache, one JSON blob per key). A seventh, `dashboard_feed`, lives in the same project but is **written by the Fitness Dashboard and only read here** — see the Fitness Dashboard feed convention below. There is also one private **Storage bucket**, `progress-photos` (2026-08-13, in `schema.sql` too), holding the Waist & Photos section's progress photos as real JPEG files, RLS-scoped to each user's own `{uid}/` folder — see the waist convention below for why the bytes must never live anywhere else.
- `tests/run-tests.js` — loads the real `<script>` block from `index.html` into a sandboxed Node `vm` context (with minimal `document`/`localStorage`/`history`/`fetch` stubs) and unit-tests the pure/state-only functions directly. Run with `node tests/run-tests.js` from the project root. Node is installed locally for this (`node --version` → v24+).

## Architecture

**Tiny hand-rolled render engine**, not a framework: every state change does a full `root.innerHTML = renderApp()` replace (see `render()`/`rerender()` near line 863, and don't skip reading the "Back button / gesture navigation" comment block right above it — it governs a lot of what "closing a screen" means throughout the file). Event handling is delegation on the root `#app` element via `data-action` (click), `data-bind` (text input, read on `input` event), `data-change` (file/select inputs), `data-enter` (Enter key). Three flat handler objects: `actions.X`, `inputActions.X`, `changeActions.X` — every `data-action="X"`/`data-bind="X"`/`data-change="X"` must resolve to a same-named entry in one of these, or it's dead on click.

**Critical ordering gotcha:** `actions`/`inputActions`/`changeActions` are declared via `const actions = {}` etc. partway through the file (~line 863 area). Any `actions.foo = ...` assignment placed *before* that declaration throws a TDZ `ReferenceError` that halts the entire script — the app just shows "Loading..." forever, on every device, with no console access on a phone to see why. This has happened before. Before any commit that adds new top-level `actions.X =` / `inputActions.X =` / `changeActions.X =` assignments, verify none of them appear above their object's `const` declaration.

**No build step = no compiler safety net.** A syntax error is a runtime failure on Colin's phone, not a red squiggle. Before every push: extract the two `<script>` blocks and run `node --check` on the big one, then `node tests/run-tests.js`. Both are fast (seconds) and are not optional — they're what catches the class of bug described above before it ships.

### Food tab screen model

`renderFoodTab()` gates on 7 mutually-exclusive flags on `state.ui.food` (via `foodUi()`), checked in priority order — first truthy one wins the whole screen: `scanningBarcode`, `loggingRecipe`, `recipeBuilder` (which itself nests a `picker` sub-state for the ingredient picker, and `picker.selecting`), `wizardType`, `showAI`, `manualEntry`, `addingFood`. Falls through to the search/history/favorites/recipes sub-tabs if none are set.

### Back-button / navigation (added 2026-07)

The app has no router. `computeNavDepth()` derives a 3-tier depth purely from `state` (0 = dashboard tab, 1 = any other tab at its base, 2 = any Food-tab sub-screen from the list above). `render()` calls `syncNavHistoryDepth()` at the top of every call, which auto-`pushState`s to match depth *increases* — no action needs to manually push history, entering any deeper screen is handled generically. Exiting a level is different: a screen's own Cancel/Back/Confirm-and-exit action must call `stepBackOneLevel()` instead of clearing its own flag directly, which triggers `history.back()`; the single `popstate` listener (bottom of file) is the one place that actually calls `collapseOneNavLevel()` and mutates state, so physical back/gesture and in-app buttons collapse identically. Actions that route through `stepBackOneLevel()` also lost the implicit double-submit guard they used to get from synchronously nulling their own flag — they carry an explicit `_confirmLock` 600ms debounce guard instead (grep `_confirmLock` for the pattern; apply it to any new confirm-and-exit action). A few transitions are deliberately *not* routed through `stepBackOneLevel()` because they're lateral swaps between two depth-2 screens, not a real exit (e.g. barcode-scan → adding-food after a successful lookup) — see the comment above `collapseOneNavLevel` for the full reasoning.

### Sync engine

Offline-first: `localStorage` is the instant source of truth; every save function also calls `scheduleCloudSync()` (debounced 2.5s) to push the full current dataset as a PostgREST upsert. `pullAndMergeAll()` runs on login and on boot and does everything in **pull → merge → push** order (settings first, then the rest). Merges are **in place** (never snapshot-and-replace-wholesale — that was a real bug), with newer-wins conflict resolution by `updated_at` for food logs and weights (recipes/customBarcodes stay additive-only). A "recently deleted" tombstone (`recentlyDeletedIds`, ~30s) stops a pull from resurrecting something just deleted locally. "Clear All Data" issues real `DELETE`s against all 6 tables — pushes are upsert-only and never delete.

**Why pull-before-push is load-bearing, not incidental (fixed 2026-07):** `favorites`/`recentFoods`/`foodCache` are each stored as one whole JSON blob in `user_app_data`, and their push is a **blind whole-blob overwrite** (additive merge, but overwriting push). If the push ran first, a device booting with an empty or truncated local store (fresh install, or iOS/PWA localStorage eviction) would overwrite the cloud master copy with its near-empty local one — silently wiping History for every device ("history is empty sometimes" — the actual reported bug). Pulling+merging first guarantees local already contains the cloud's data before any push, so the push always sends local-unioned-with-cloud, never a subset; it also makes food-log newer-wins correct (the blind id-upsert can't clobber a newer cloud edit). `pullAndMergeAll` also **bails before pushing if any pull errored** — pushing on top of a failed pull is exactly the clobber risk; the debounced per-save sync still covers un-pushed local changes. Do not reorder this back to push-first, and do not add a new whole-blob collection without keeping it inside this pull-first flow.

**keepalive has a hard 64KiB body quota, and blowing it is a silent client-side rejection (fixed 2026-07-28 — the "weights never reach the database" outage):** `fetch({keepalive:true})` with a body over ~64KiB (quota SHARED across in-flight keepalive requests) rejects immediately with a bare TypeError and **no network request at all** — nothing in server logs, and before v1.10 nothing in the app either. The weights push sends the entire history each time (~170KB after the multi-year Renpho CSV import), so the day `keepalive: true` shipped in `supabaseTable`, every weight push started dying pre-flight; food kept working only because its payload was smaller (and was itself ~1KB from the cliff). Fix: `fitsKeepaliveQuota(bodyStr)` (UTF-8 bytes via `utf8ByteLength`, budget `KEEPALIVE_BODY_BUDGET_BYTES` = 24000 so a few concurrent pushes can share the real 64KiB) gates the flag, and a keepalive fetch that rejects pre-flight is retried once **without** keepalive (nothing was sent, so no duplicate risk). Diagnosed from the Supabase side: `weight_entries` frozen at Jul 17 while `food_log_entries` was current, and zero weight POSTs in the API logs — absence of failures, not presence of them, was the tell. Don't "simplify" the gate away: the original code's comment confidently said bodies were "well under" the limit on the very day the weights payload was 2.7× over it.

**Debounce vs. backgrounding (fixed 2026-07)**: the 2.5s debounce was a real data-loss window — logging food and immediately backgrounding/locking the phone (completely normal usage) could kill the pending push before it fired, leaving that entry stranded in local-only storage on one device with no cloud copy. Fixed two ways: `scheduleCloudSync` now tracks the pending push function in `pendingSyncPushFns` alongside its timer, and `flushPendingCloudSyncs()` (wired to both `visibilitychange`→hidden and `pagehide`) fires any still-pending push immediately instead of waiting out the timer; `supabaseTable`'s fetch also sets `keepalive: true` so an in-flight request survives the page actually being torn down, not just backgrounded. Any new debounced-write pattern should route through `scheduleCloudSync` rather than rolling its own timer, or it won't get this protection.

**New field on a table-backed row (not a whole-blob collection) needs a real column, and check before shipping.** `food_log_entries` is a fixed-schema table — adding a JS field like `entry.brand` and just including it in `flattenFoodLogsForSync`'s payload before the column exists would make PostgREST reject the *entire* push (unknown column), silently breaking sync for that whole table until fixed. `entry.brand`/`entry.animalOverride` (added 2026-07) shipped **local-only** at first for exactly this reason, then Colin ran the `alter table` migration from `supabase/README.md` and the fields were wired into `flattenFoodLogsForSync`/`pullFoodLogsFromCloud`'s `select=`/`mergeFoodLogsFromCloud` (mirroring calories/protein/etc.) — they now sync and round-trip normally. Two details worth keeping if you touch this: (1) `flattenFoodLogsForSync` sends `brand`/`animal_override` as explicit `null`, never an omitted/`undefined` key — PostgREST's bulk upsert turns the whole batch into one `INSERT` with a shared column set, so an inconsistent key across rows in the same push is a real risk, not just untidy; (2) `row.animal_override == null ? null : row.animal_override` on the pull side specifically preserves a real `false` (a manual "this is plant protein" call), which `row.animal_override || null` would have collapsed into `null` and silently reverted to auto-guessing. This is the template for any future column: **verify against `supabase/schema.sql` first**, and if it's not there yet, ship the JS field local-only (excluded from the sync payload) and ask before wiring it into the push/pull/merge trio.

**The backup contract is declared in one place and enforced by tests (added 2026-08-10).** `PERSISTED_COLLECTIONS` (right under the `save*` functions, ~line 318) lists every collection of Colin's data that has to survive a reinstall, with its localStorage key and its `push`/`pull`/`merge` function names; `NON_BACKED_UP_KEYS` lists the three deliberate exclusions (`supabaseSession` = a credential, `pendingDeletes` = device-local machinery, `dashboardFeed` = another app's rows). `tests/run-tests.js` walks the registry and fails if any entry is missing from `exportSnapshot`, `importData`, `clearAllData`, or `pullAndMergeAll`'s pull/push lists — **and separately scans `index.html` for every key read or written through `db`, failing on any that isn't declared in one of the two lists.** That reverse scan is the point: "is everything backed up?" used to be answerable only by reading six places and noticing an omission, which is exactly the check a human skips, and the cost is silent (nothing breaks, the data just isn't there on the next device). `foodCache` went missing from the export this way. **Register a new collection here first** — and note the scan is literal, so don't write a `db.get`/`db.set` call with a placeholder key inside a comment.

**Both remaining additive-only merges became newer-wins (fixed 2026-08-10).** `recipes` and `custom_barcodes` were the last two collections merged by "add it if the id is missing, otherwise keep local forever." That isn't a merge, it's a one-way import, and it cost real edits in both directions: an edit made on one device could never reach a device that already had that row, **and** because both pushes are blind id-upserts, the stale device then pushed its old copy straight back over the edit. The change wasn't just invisible on one screen — it was destroyed in the cloud on the next sync from anywhere else. Both now use `foodRecordIsNewer`, the same `updatedAt` rule the food logs and the whole-blob food lists use, and neither needed a migration: `recipes.updated_at` already existed (see the corrected note under Known deferred items), and `custom_barcodes` has no such column but its `food` payload is **jsonb**, so the stamp rides *inside* the blob. Two things to keep: every custom-barcode write path (`saveBarcodeCorrection`, `saveEditBarcode`, `saveCustomBarcode`, and `propagateCustomFoodEdit`'s barcode branch) must stamp `food.updatedAt` or its correction can never win a merge — there's a test asserting exactly that; and both merges stay backward-compatible by construction (a cloud copy only wins by claiming a genuinely *newer* stamp, so unstamped rows behave exactly as before and convergence phases in as things are touched).

## Conventions

- **What Colin logs is the truth — no inflation/deflation, ever** (Colin's rule, 2026-08-03; binds MacroLog **and** the Fitness Dashboard, which documents it in full under its own "What Colin logs is the truth" heading). Whatever he enters for calories and macros is taken as exact. MacroLog must never model the accuracy of its own log: no under-reporting/over-reporting correction applied to a day's total or a target, no weighting a food by its `source` (an `"AI Estimate"` entry counts identically to a weighed one — `source` is provenance, used for finding and correcting an entry and nothing else), no plausibility rescaling, and no copy suggesting his logging runs high or low. This is currently true of the whole app; the note exists so it stays that way. It is load-bearing downstream: the dashboard solves ONE energy-balance equation to pin down what each activity actually burns, and intake sits on the other side of that equation — a hidden intake adjustment here is mathematically indistinguishable from a burn error there, and would quietly absorb the very number the calibration exists to find. Still allowed, because none of it adjusts what he said: flagging a single obviously impossible entry, and the AI estimator's pre-confirmation confidence (he reviews and corrects the proposal before it's committed).

- Text inputs deliberately do **not** trigger `rerender()` on keystroke (would steal focus mid-type) — `inputActions.X` handlers patch specific DOM elements directly (e.g. flipping a button's `disabled`) instead of re-rendering. This is a recurring source of "button doesn't update" bugs when adding a new input; check for this pattern before assuming a fresh flag will "just work."
- **Serving-size quantity selection** (added 2026-07): the three "pick a food, then set how much" screens (Adding Food, recipe ingredient picker, wizard result) share `renderServingControls`/`computeQtyWeight`/`patchMacroPreview` (near `macroStat`, ~line 2338). Tapping a serving chip (e.g. "1 cookie (33g)") sets a `servingBasis` and switches the input to a quantity ("2" → 66g) instead of raw grams; "Enter grams instead" clears `servingBasis` to go back to typing grams directly. Each screen keeps its own `weight`/`servingBasis`/`qty` trio in its own UI sub-object (`fu.addWeight`/`addServingBasis`/`addQty`, `pk.weight`/`servingBasis`/`qty`, `wiz.weight`/`servingBasis`/`qty`) — all must be reset together (`servingBasis = null; qty = "1"`) at every point a new food is selected/estimated, or a stale quantity basis will carry over to an unrelated food.
- **Auto-calculated calories** (added 2026-07): Manual Entry and the "barcode not found" custom-entry screen both derive calories from protein/carbs/fat via `calcCaloriesFromMacros` (Atwater 4/4/9, same factors as the Strategy tab's target math) — editing any of the three macro fields recomputes and DOM-patches the calories input. Editing calories directly still works and isn't overwritten unless a macro field is touched again afterward (it's a one-way derivation, not a two-way lock).
- **Search-as-you-type, two separate groups** (2026-07): the Search sub-tab renders **two independent lists**, patched into `#foodResultsBlock` via `patchFoodResultsBlock()` rather than a full `rerender()` (which would blur the input mid-keystroke). `fu.historyResults` = "★ Eaten before" (from `localFoodMatches(q)`: a synchronous substring match over `recentFoods`/`favorites`/`foodCache`, no network, fires from the **1st** character) renders on top; `fu.results` = "Food databases" (USDA + Open Food Facts via debounced `liveFoodSearch(q, mySeq)`, 450ms after the last keystroke, 3+ chars to spare USDA's shared rate-limited demo key) renders underneath. **Keep these two lists separate** — they used to be concatenated through `deduplicateFoods` together, which folded an already-eaten food into a database row and destroyed its "you've had this before" identity. `dbResultsExcludingHistory(history, dbFoods)` de-dupes USDA-vs-OFF *within* the database group and drops anything already shown in the history group by id, so nothing appears twice. Both this and the explicit tap/Enter path (`doFoodSearch`) share one module-level `foodSearchSeq` counter bumped on every keystroke/explicit search; an in-flight request checks its captured `mySeq` before applying results, so a slow older request can't clobber a newer one — preserve that guard. `selectFoodForAdd` must search `fu.historyResults` too (those rows can originate from favorites/foodCache, not just `recentFoods`).
- **Saved recipes are a search result, not just a sub-tab** (2026-07-28): a recipe used to be reachable only by opening Food > Recipes and reading down the list. `renderFoodResultGroups` now renders **three** groups, most-specific first — "🍲 Your recipes", then "★ Eaten before", then "Food databases" — and the caller supplies `recipeAction` alongside `action` (Food tab → `logRecipe`, which drops into the existing log-recipe weight screen; ingredient picker → `selectIngredientRecipe`, which nests the recipe into the one being built). `matchingRecipes(q)` matches on **name only** (a recipe has no brand, and matching ingredient names would surface "Chili" for a search of "onion" with no way for the row to explain itself). Two things to preserve: (1) `historyExcludingRecipes(recipeList, historyFoods)` drops the `recipe_food_<id>` snapshot that logging a recipe leaves in `recentFoods`, so the same name can't render in two groups — note the tiebreak runs **opposite** to `dbResultsExcludingHistory` (there history wins; here the recipe row wins, because it re-reads the recipe's current ingredients while the snapshot is frozen at whatever the recipe looked like the day it was logged); (2) the empty-results message keys off "all three groups empty", so a recipe-only match must not print "No results". `recipeAsFood(recipe)` flattens a recipe into one food anchored by `baseGrams` = the recipe's own total weight (via `positiveGramsOr(t.weight, 100)`, so an unweighed recipe can't produce a 0g base) — that's what lets a nested recipe scale to a partial portion through the normal `calcMacrosForWeight` path with no special case in `confirmAddIngredient`. `pickerRecipeMatches(rb, q)` excludes `rb.editingId` so a recipe can't be nested inside itself. The Recipes sub-tab also gained its own filter box (`recipesQuery` → `renderRecipesListBlock` patched into `#recipesListBlock`), mirroring History/Favorites. The wizard's search is deliberately *not* included: its query is derived from the guided selections, not typed, and it exists to find a database record for a specific cut/preparation.
- **The recipe ingredient picker uses that same search** (2026-07-28): it used to hit USDA/Open Food Facts only, on an explicit tap/Enter, so a food Colin had entered by hand or eaten before was unreachable while building a recipe even though it was one tap away on the Food tab. The two-group body is now one shared renderer, `renderFoodResultGroups({history, dbResults, searching, query, action, emptyText})`, called by both `renderFoodResultsBlock` (which still owns the wizard-suggestion banner above it) and `renderIngredientResultsBlock`; `foodResultRow(food, srcTab, action)` grew the 3rd param purely so the picker's rows can target `selectIngredientFood` instead of `selectFoodForAdd`. Keep them on the one renderer rather than forking a parallel copy — the fork is what let them drift. The picker mirrors the Food tab's mechanics too: local matches from the 1st character, debounced 450ms/3+ char database search, patched into `#ingredientResultsBlock` via `patchIngredientResultsBlock()` (never `rerender()` — see the no-rerender-on-keystroke rule), and `selectIngredientFood` searches `pk.historyResults`/`recentFoods`/`favorites`/`foodCache` in the same defensive order `selectFoodForAdd` does. It carries its **own** `ingredientSearchSeq`/`ingredientSearchDebounceTimer` (not the Food tab's, so neither can invalidate the other's in-flight request) plus an `ingredientPickerIsCurrent(pk)` identity check — the picker object is recreated on open and nulled on close, so seq alone wouldn't stop a late response writing into a detached picker.
- **The ingredient picker can browse History and scan a barcode, not just search** (2026-07-30): the picker's modes are now `search` / `history` / `favorites` / `manual`. Search already surfaced a previously-eaten food from the 1st character, but only if you could remember enough of its name to type — History is the durable 500-entry "everything ever added" list, and *scrolling* it is how you find the one you can't name. `renderPickerHistoryListBlock(pk)` filters `state.recentFoods` through the shared `filterFoodsByQuery`, patched into `#pickerHistoryListBlock` from `inputActions.pickerHistoryQuery` (never `rerender()` — the no-rerender-on-keystroke rule). It keeps its **own** `pk.historyQuery` rather than reusing the Food tab's `fu.historyQuery`, so the two screens' filters can't leak into each other. History and Favorites share one row renderer, `pickerBrowseRow(food, srcTab)` — same reason the search body is shared: a forked copy is what let the picker drift from the Food tab in the first place.
- **Scanning a barcode into a recipe forks at exactly one place** (2026-07-30): `actions.openIngredientBarcodeScan` deliberately does **not** reuse `actions.openBarcodeScan` — that one resets `state.ui` wholesale, which would throw away the half-built recipe. Since `renderFoodTab` checks `scanningBarcode` *before* `recipeBuilder`, simply raising the flag swaps the camera screen in on top of the untouched builder: a lateral move between two depth-2 screens (same reasoning as barcode-scan → adding-food), not a new nav level, so backing out lands on the picker instead of dropping the builder. Everything downstream — camera, manual-code box, `customBarcodes` lookup, the not-found form — is shared verbatim; the **only** fork is `deliverScannedFood(food, weightStr)`, which reads `fu.scanTarget` (`"ingredient"` vs. null) to decide between `pk.selecting` and `fu.addingFood`. Route any new "scan produced a food" path through it rather than assigning `fu.addingFood` directly, or that path will silently log to today's log while the user is building a recipe. Two guards are load-bearing: it **drops** a delivery when `fu.scanningBarcode` is already false (a lookup still in flight when the user backs out would otherwise drag them into a screen they'd left — and on the ingredient path the fallback isn't a no-op, it's logging the food to today), and an ingredient delivery whose picker vanished mid-lookup closes out silently rather than falling back to `addingFood`. `collapseOneNavLevel` clears `scanTarget` alongside `scanningBarcode`.
- **Plant-protein estimate** (added 2026-07): the dashboard's Protein bar shows a "(Xg plant-based)" sublabel, same spot fiber annotates the Carbs bar. Unlike fiber, no database provides this — `isAnimalProteinFood(name)` (near `getDayTotals`, ~line 1214) is a keyword regex guess against the logged entry's name (meat/dairy/egg/fish all count as animal, per Colin's call — eggs and fish aren't literally meat or dairy but count the same way). It's computed live in `getDayTotals`, not stored or synced, so it applies retroactively to old entries and needed no schema change — but it's a heuristic: a mixed dish matching any animal keyword is attributed entirely to animal protein (floor, not exact), and an unrecognized packaged/branded name with real animal protein could be missed. Keep new keywords `\b`-word-boundary-wrapped (`egg` must not match inside `eggplant`) and add solid compound words explicitly when boundary matching can't catch them (`milkshake`, `cheeseburger`, `hamburger` — no boundary exists between the two halves).
- **Per-day macro boosts are SIGNED** (2026-07-29): a boost can also *remove* grams (rest days / banking a deficit) — `dayBoostFor` must not clamp negatives on read, and `bumpDayBoost` floors each macro at `-(base target)` so the effective target bottoms out at exactly 0 (`getDayTargets` also hard-floors all four targets at 0 — the progress bars divide by them). Labels go through `signedKcal` ("+320"/"−240"). All-zero-means-off tombstone semantics unchanged.
- **7-day deficit/surplus log** (2026-07-29, two-yardstick since 2026-08-15): `weeklyDeltaLog(endDateStr, days)` + `renderWeeklyDeltaCard` at the bottom of the dashboard. Every row now carries **both scorings**: `target`/`delta` vs the **base** goal standing that day (`targetsForDate`), and `dayTarget`/`dayDelta` vs the target actually **set** for the day (`getDayTargets` — base + ⚡ activity boost). The rows display a target column (⚡-marked when boosted) and `dayDelta` — matching what the day's own progress bar said, instead of contradicting it — while the bottom shows the "vs day targets" net **plus a second "vs standing goal (no ⚡)" net whenever a logged day was boosted**. That second line is load-bearing: the original design scored *only* against base because a target that moves with each day's boost lets a boost hide the surplus it budgeted for — the standing-goal counter must stay visible on boosted weeks, so don't "simplify" it away (and on boost-free weeks the two are identical, so it renders as the single familiar net). Days with no entries are shown as "no log" and **excluded from both nets** (an unlogged day is missing data, not a 1,900-kcal deficit). Window anchors to the *viewed* day (`state.date`), calendar-day stepping via `parseDateStr`/`setDate`.
- **PNG manifest icons are generated, not hand-drawn** (2026-07-29): `icon-192.png`/`icon-512.png` are rasterized from the logo artwork (dark full-bleed tile, mark at 68% — inside the maskable safe zone; `purpose: "any maskable"`). Regenerate via `npx sharp-cli` from an SVG with the same two paths as `logoSvg()`; validate PNG chunk CRCs and sample pixels before committing (a hand-transcribed or corrupted binary passes `git add` silently). An already-installed PWA updates its icon only when the WebAPK refreshes or on reinstall.
- **Per-day macro boosts** (added 2026-07-28): heavy-activity days can raise ONE day's targets — `state.dayBoosts` maps date → `{protein, carbs, fat, updatedAt}` (grams on top of base; calories derive via Atwater in `boostCalories`). **`getDayTargets(date)` is the single source of a day's effective targets** — the dashboard and the Food tab's mini-summary both read it; anything new that renders "X of Y kcal" must too, or boosted days disagree between screens. Base targets in `state.settings` are never touched. - **`calcMacrosForWeight`'s base-grams bug (fixed 2026-07): what portion do a food's stored macros describe?** Database foods (USDA/OFF) are per-100g (`per100g:true`). Everything the user *creates* (Manual Entry, AI Estimate, Recipe, custom barcodes) stores **absolute** macros for one specific portion instead — the portion is recovered via `foodBaseGrams(food)`: `per100g` → 100, else `servingSizes[0].grams`, else `loggedWeight`, else 100 as a last resort. - **`baseGrams` is the explicit base-portion anchor (added 2026-07-25) — the fix for "sometimes the macros don't scale when I change the weight".** `foodBaseGrams(food)` now checks `food.baseGrams` **first**, ahead of `per100g` / `servingSizes[0].grams` / `loggedWeight`. Those three are only *inferences*, and each is derived from a field some other code path legitimately overwrites — so either one could silently re-anchor a food to a portion its numbers never described. Two real bugs came from exactly that: **(1)** `propagateCustomFoodEdit` wrote a macro correction back to the food record without moving the base — correct a manual food's macros while the entry sits at 166g and the record still claimed its original 83g base, so a later portion change to 83g re-derived *the exact same numbers* (visibly "didn't scale") and 166g doubled them; **(2)** `confirmAddFood`/`wizardConfirmAdd` overwrote `loggedWeight` when re-logging, and for a food with no `servingSizes` (every AI Estimate, every recipe log) `loggedWeight` **was** the inferred base — so a 400g/500kcal item re-added at 200g and then back at 400g came out as 1000 kcal, compounding on every round trip. Two rules follow: **call `anchorFoodBase(food)` before overwriting `loggedWeight`** on a clone (that's why it lives at the clone sites and not inside `addFoodToLog` — by the time `addFoodToLog` runs, the anchor is already gone), and **when corrected macros describe a different portion, move `baseGrams` with them**. `baseGrams` lives only on food objects in `recentFoods`/`favorites`/`foodCache` (→ the `user_app_data` JSON blob) and `customBarcodes` (→ `custom_barcodes.food`, a **jsonb** column) — it never touches `food_log_entries`, so **no schema migration was needed**. Records already drifted by bug (2) before this shipped keep their drifted numbers (the original is unrecoverable); fix those by hand via History → ✎ Edit.
- **A portion change must not silently discard an entry-only macro correction** (2026-07-25): `saveEntryPortion` used to always re-derive from `state.foodCache[entry.foodId]`, which threw away a hand correction made on the Macros tab — the same tab that promises "this only changes today's entry". `rescaleEntryMacros(entry, newWeight)` re-derives from the source food **only when `entryMatchesFood(entry, food)`** (the entry's macros still equal what the food predicts at the entry's current weight, within rounding tolerance); otherwise it scales the entry's own macros proportionally. Re-deriving is preferred where it's valid because it scales from the food's own base rather than from already-rounded per-entry numbers. `entryMatchesFood` checks fiber too — it's an editable field, and omitting it would classify a fiber-only correction as "unmodified" and revert it. - **Deletes are a durable queue, not fire-and-forget** (2026-07-26): `scheduleCloudDelete` used to issue the DELETE and discard the result, with only a 30s in-memory tombstone (`recentlyDeletedIds`) stopping a pull from re-adding the row. A delete made offline, with an expired token, or simply lost, left the row alive in the cloud; once the tombstone aged out — or the app reloaded, which drops it entirely — the next pull silently restored the deleted food. `pendingDeletes` (persisted to `localStorage`, kept in memory as the source of truth) is enqueued *before* the attempt and only dequeued on confirmed success; `wasRecentlyDeleted` treats a queued delete as a tombstone **regardless of TTL**, so a row can't come back while its removal is outstanding. `flushPendingDeletes()` runs at the **start** of `pullAndMergeAll`, before anything is pulled — pulling first would merge the row straight back. Don't re-read the queue from storage per call: `wasRecentlyDeleted` consults it once per row of every pull, and `flushPendingDeletes` retries with `Promise.all`, so a load-filter-save would both thrash and let concurrent dequeues clobber each other.

- **The barcode scanner confirms a code across frames before acting on it** (2026-08-10): reported as "you scan too quickly and think the barcode can't be read — scanning again works." Saves go through `updateFoodRecordEverywhere(foodId, updates)`, which propagates the correction into `favorites` and `foodCache` too when the same id is cached there, so re-adding the food from *any* list uses the fix. When correcting macros specifically, also rescale `loggedWeight`'s `loggedMacros` snapshot to the new base (`calcMacrosForWeight` at the same weight) — `addFoodToLog` prefers `loggedMacros` over the base fields whenever both exist, so skipping this would leave the stale numbers winning on the next re-add. `macroEditField` takes an optional 4th `enterAction` param (default `"saveEditMacros"`) specifically so this screen could reuse it with `"saveFoodRecordMacros"` instead of duplicating the markup.
- **Weight stat cards can follow the chart's selected range (2026-07)**: Avg Daily/Weekly Change normally reflect "since your starting point" (`effStartDate`/`effStartWeight`, unchanged, always-on default). Tapping a 7d/30d/90d/6m/All chip (`setWeightRange`) arms `wu.statsFollowsRange` and switches *only* those two cards to the chart's currently-filtered `chartData` window via the pure `weightRangeStats(data)` helper (first-vs-last point; null below 2 points) — Current Weight/Total Change are untouched, matching what was actually asked for. Tapping the Current Weight card (`resetWeightStatsRange`) disarms it back to starting-point mode *without* changing which range the chart displays — those are deliberately two independent pieces of state (`wu.timeRange` vs. `wu.statsFollowsRange`). `chartData` was moved earlier in `renderWeightTab` (previously computed below the stat cards) so both consumers share one computation. The selected-point popup shows the year too when `wu.timeRange === "all"`, since only that tab can span multiple years.
- **`weightChartCutoff`'s calendar-day bug (fixed 2026-07)**: the 7d/30d/90d/6m chip cutoffs used to be `Date.now() - N*86400000` compared against each entry's local-midnight timestamp — since `Date.now()` is a moving clock-time, not a calendar boundary, the cutoff fell partway through a day rather than at midnight, and whichever calendar day it sliced through got silently excluded depending purely on what time of day the chart happened to be viewed (reported as "7d seems to start from Monday" — reproducible whenever "today" is a Sunday, since the boundary then always lands after that Sunday's own midnight one week back). Fixed via `weightChartCutoff(timeRange, referenceDateStr)`: pure, date-string-in/timestamp-out, anchored to `state.date` (not the wall clock) via `setDate()` (not raw ms subtraction, which is also DST-unsafe — a "day" during a DST transition is 23 or 25 hours). **Any new date-range filter in this app should use this same pattern** (calendar-day arithmetic via `parseDateStr`/`setDate`, never `Date.now() - N*86400000`) — the raw-ms-subtraction bug is easy to reintroduce by "simplifying" this back.
- **The Fitness Dashboard feed is READ-ONLY and in SHADOW MODE (added 2026-08-02)**: Colin's other app (the Fitness Dashboard — separate repo, separate database, COROS activity data) publishes one row per day into `dashboard_feed` in *this* project: calibrated activity burn, the calorie target it would recommend, and its rolling measured TDEE with an uncertainty band. `pullDashboardFeedFromCloud` → `mergeDashboardFeedFromCloud` → `state.dashboardFeed` (date-keyed, localStorage-cached) → `renderDashboardFeedBlock`, which draws a block under the targets card on the dashboard. Four things are load-bearing: **(1) there is no push, no save\* helper and no DELETE for this collection, and it must not grow one** — the dashboard recomputes and re-upserts those rows, so anything written from here is overwritten on its next publish, and two writers on one table is exactly the conflict class the sync engine exists to avoid (`clearAllData` clears the local cache with a direct `db.set` for this reason, and deliberately does not DELETE the cloud rows — they aren't MacroLog's to destroy). **(2) `feedPull.error` is deliberately EXCLUDED from `pullAndMergeAll`'s `firstError`** — every other pull aborts the sync before the push, which is right for MacroLog's own data, but letting another app's table join that guard means a missing table, an RLS hiccup or a dashboard that has simply never published would silently stop food and weights from syncing. There's a test that fails if this is "tidied up" (proved by re-adding `|| feedPull.error` and watching it go red). **(3) It is shadow mode: `getDayTargets` does not read the feed**, so the big number and every progress bar are still MacroLog's own targets — the recommendation sits beside them as a second opinion and acting on it is a manual ⚡ tap. Wiring it into the target means a number Colin never chose moving his calorie goal whenever a watch syncs; that's a deliberate future step with its own switch, not a side effect of being able to read the feed. **(4) Absent is not zero** — `dashboardFeedFor` returns `null` for a day with no row (renders nothing, rather than an empty framed block) and keeps `tdee` `null` while the dashboard's estimate is still gated on too little data, so a gated estimate can never render as "0 kcal maintenance".
- **Macro-editor calories is a real, overridable field now, not always re-derived (fixed 2026-07 — "how do you handle alcohol calories?")**: alcohol contributes ~7 kcal/g that protein/carbs/fat can't represent at all, so a food containing it needs an editable calories number, not one silently recomputed from Atwater math on every save. Both `renderEntryEditor`'s Macros tab and `renderFoodRecordEditor`'s Macros tab now render a `editMacroCaloriesInput` field auto-calculated live as protein/carbs/fat change (via `patchEditMacroCalories()`, wired through `inputActions.editMacroProtein/Carbs/Fat`) but freely overridable by typing into it directly — exactly Manual Entry's existing pattern, just extended to these two editors. `saveEditMacros`/`saveFoodRecordMacros` now read `editMacroCaloriesInput`'s value directly as the saved calories, instead of always computing `Math.round(p*4+c*4+f*9)`. `macroEditField` grew an optional 5th `bindAction` param for this (only protein/carbs/fat pass one — fiber deliberately doesn't, since it isn't part of Atwater calories). Both editors share the same `editMacro_*` element ids and `inputActions`, which is safe because the two screens are never on-screen simultaneously (Dashboard tab vs. Food tab).

- **Waist measurements + progress photos (added 2026-08-13, Strategy > Waist & Photos)**: `state.waistEntries` maps date → `{waist, notes, photos, updatedAt}` — one entry per date, synced as a `user_app_data` blob under `'waistEntries'` (no table migration), per-date newer-wins via `foodRecordIsNewer`, registered in `PERSISTED_COLLECTIONS`, deletes/date-moves written as **empty-entry tombstones** with a fresh stamp (`waistEntryIsEmpty` is the single test; same trick as dayBoosts' all-zero). The waist unit follows `settings.weightUnit` (lbs→in, kg→cm). **`photos` holds Supabase Storage PATHS (`"uid/filename.jpg"`), never image bytes** — inline base64 was the first design and ~30 photos would have exhausted the ~5MB localStorage quota *shared with food and weight logs*, making photo growth take core logging down with it. The bytes live as files in the private `progress-photos` bucket; the only data-URL strings that ever exist are in the form's pending list (`isPendingWaistPhoto`), compressed on-device (1600px/q0.8) and uploaded **before** the entry is written, so an entry can never reference a file that doesn't exist — which also means photo saves are the app's one deliberately online-only write (Colin's call; a save with no new photos stays offline-first). Display is placeholder-`<img data-photopath>` → authenticated fetch → object-URL cache → **direct DOM patch, not rerender** (resolves at arbitrary moments, possibly mid-keystroke in the notes box). Four edges that must stay wired: the **export inlines every photo's bytes** under `waistPhotoData` (paths alone are not a backup) and `importData` re-uploads them, rewriting the `{uid}/` segment for a cross-account restore; **Clear All Data wipes the bucket folder** via `listProgressPhotoPaths`; file deletes are **best-effort with no retry queue, on purpose** — the failure mode is an invisible orphan file (free at this scale), not a resurrected row, so the `pendingDeletes` machinery would buy nothing; and there's a source-contract test pinning export/import/clear to all of this.
- **Weight chart: Manual range + panning (added 2026-08-13)**: a sixth "Manual" chip (all six compressed to one line) opens an inline day-count popup — inline rather than a floating modal because the delegated click handler would need a click-swallowing layer (a tap inside a centred modal bubbles to the backdrop's action). The chart window is now an inclusive `[startMs, endMs]` pair from `weightChartWindowBounds(timeRange, manualDays, panOffsetDays, referenceDateStr)` — **panning slides both ends**, so newer entries drop out too; `weightChartCutoff` survives only as a wrapper over its start (old callers/tests). `wu.panOffsetDays` is how many days the window's end sits behind `state.date`, moved by ‹ › buttons (half a window) or a horizontal swipe on the `[data-panzone]` chart wrapper (root-level passive touch listeners, commit-on-touchend — per-frame panning would mean a full rerender per touchmove; mostly-vertical gestures are left to the browser as scrolls, and `chartPanClickGuard` stops a swipe's tail click from selecting a point). It's **re-clamped against the real data span every render** (`clampWeightPanOffset` — deleting weigh-ins or widening the range can't strand the window), and the history card is gated on `allWeights.length > 1`, not the window's contents, so panning into a logging gap shows a placeholder with the controls still present instead of a dead end. All the window math is pure and calendar-day-stepped (`parseDateStr`/`setDate`, DST-safe — same rule as the original `weightChartCutoff` fix).

## Deploy

**Before every commit that ships a real change**, bump `APP_VERSION` (near the top of `index.html`, ~line 170) up by `0.01`. It's shown at the bottom of Strategy > Data ("MacroLog vX.XX") specifically so Colin can glance at his phone and tell whether a push actually landed, instead of guessing against a possibly-stale service-worker cache — an unbumped version number after a push silently defeats the entire point of it. Started at `1.0` (2026-07); do not skip this step, and do not bump it for something that isn't actually shipping (e.g. a revert-only commit, a pure `.md` edit).

`git push origin main` → GitHub Pages auto-builds, typically live within 1–2 minutes. No CI, no staging slot. Verify a push landed with a direct fetch, e.g.:
```powershell
(Invoke-WebRequest -Uri "https://colinswhardy.github.io/claudemacro/index.html" -Headers @{"Cache-Control"="no-cache"}).Content -match "some-string-from-the-change"
```
